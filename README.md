# FC Altynka — Telegram-бот + мини-апп

Бот ведёт сбор на игру одним самообновляющимся сообщением в группе: запись кнопкой «Иду», резерв, назначение времени,
составы и счёт. Мини-апп — для деталей, составов, счёта, игровых профилей и оценки матчей.

- Дизайн: `docs/superpowers/specs/2026-11-03-football-sbor-bot-design.md`
- План: `docs/superpowers/plans/2026-11-03-football-sbor-bot.md`
- Текущий интерфейс: [`DESIGN.md`](DESIGN.md), [план переноса Airofit](docs/superpowers/plans/2026-11-04-airofit-app.md).
- Игровые характеристики и анонимные оценки: [правила](docs/superpowers/specs/2026-11-05-player-ratings-design.md), [проверка реализации](docs/player-ratings-review.md).
- Сообщения и команды бота: [сценарии](docs/bot-copy-draft.md), [реализация и доставка](docs/bot-delivery-review.md).

## Разработка

```bash
pnpm install
pnpm test          # все тесты
pnpm typecheck     # проверка типов
pnpm build         # сборка мини-аппа
pnpm test:ui       # production-сборка, мобильные экраны и доступность (Playwright/axe)
pnpm test:connectors # локальные тесты Telegram MCP
pnpm check:telegram # диагностика реального бота без отправки сообщений
pnpm bot:profile   # показать план оформления бота без сетевых изменений
pnpm channel:post  # проверить пост для канала новостей; публикация только с --apply
```

Локально: `cp apps/worker/.dev.vars.example apps/worker/.dev.vars`, затем
`cd apps/worker && pnpm exec wrangler d1 migrations apply fc-altynka --local && pnpm exec wrangler dev`.
Мини-апп в браузере: `pnpm --filter @altynka/miniapp dev` (проксирует `/api` на `localhost:8787`).
Без Telegram мини-апп покажет «Открой мини-апп из Telegram» — это нормально.

В группе бот публикует общие объявления, составы и компактный счёт. Личные уведомления игрок включает в `/settings`
в личке бота или в профиле миниапки. По умолчанию они выключены. Подписчику бот пишет лично, когда открыта запись
на новый матч (с кнопкой «Иду»), назначены или изменились время и поле, матч отменён, он перешёл между основой и
резервом, опубликованы составы (с его командой), до матча два часа, выставлен счёт и можно оценить игру.
Сразу после завершения встречи со статистикой каждый сыгравший подписчик получает личные итоги: свои голы,
передачи, результат коротких игр и уровни достижений, открытые этой встречей.
Объявление о новом матче получают все подписанные участники группы, кроме создателя; рассылка идёт порциями.

Личный чат с ботом — рабочий экран, а не только кнопка запуска: `/start` показывает ближайший матч, место в
очереди, сумму к оплате и состояние уведомлений; записаться и отменить запись можно кнопкой прямо в сообщении.
Кнопки меню перерисовывают то же сообщение, обычный текст без команды открывает меню.
Команды в личке: `/start`, `/matches`, `/payments`, `/settings`, `/help`; организаторам дополнительно `/newmatch`.

Новости проекта выходят в канале [@fc_altynka_news](https://t.me/fc_altynka_news). Пост публикует бот:
`pnpm channel:post <файл>` проверяет текст и ничего не отправляет, с `--apply` публикует. Порядок работы и правила
текста описаны в навыке `.claude/skills/channel-post`, опубликованные посты записываются в
[`docs/channel-posts.md`](docs/channel-posts.md).
Для применения имени, описания, меню и областей команд после обновления обработчиков: `pnpm bot:profile --apply`.
Скрипт не меняет вебхук и аватар. Диагностика `pnpm check:telegram` читает также команды для лички и группы;
пустой default scope сам по себе не означает, что команды не настроены.

Разбор архитектуры, обновление UI, состояние интеграций и ограничения проверки:
[`docs/project-audit.md`](docs/project-audit.md). Визуальные правила: [`DESIGN.md`](DESIGN.md).

## Игровые рейтинги

При входе участник получает предложение пройти анкету из восьми навыков (1–10).
Стартовый рейтинг — среднее ответов; далее учитываются до десяти последних матчей
с достаточным числом оценок. Анкета имеет вес трёх матчей. Один и тот же рейтинг
с точностью до десятых показывается в профиле и используется при делении команд.

Организатор отдельно подтверждает завершение игры и фактических участников.
Им открывается анонимный опрос на 72 часа. Среднее публикуется при минимум трёх
голосах; оценка игры в целом не влияет на игроков. Список игроков и игровые профили
доступны всем участникам группы. Авторы отдельных чужих оценок API не раскрывает.

Для включения нужна миграция `0008_player_ratings.sql` **перед деплоем Worker**.
Она сохраняет прежние уровни и помечает существующие матчи как не имеющие опросов.
Следующие матчи включают опросы автоматически. Пользователи без анкеты получают
прежний уровень как предварительный. Опубликованные составы не меняются вслед
за пересчётом рейтинга. Ручное изменение вычисляемого уровня удалено.

## Игровая статистика

В интерфейсе **матч** — это весь сбор (запись, составы, оплата), а **игра N** — короткая
игра внутри него. Слово «встреча» в приложении не используется.

Новые матчи начинаются по кнопке организатора **«Начать матч»** во вкладке
«Составы». До нажатия доступны запись, гости, балансировка и ручные перестановки,
даже если назначенное время уже наступило. Старт фиксирует команды на весь матч
и случайно выбирает первую пару. После старта менять участников и составы нельзя.

Во вкладке «Игры» организатор после каждой короткой игры записывает результат и
забивших. Можно указать несколько голов одного игрока или гостя (кнопка «… ещё раз» повторяет предыдущего автора), а неизвестного
автора дополнить позже. Приложение считает таблицу (3/1/0 очка), мячи, разницу
голов и бомбардиров. Результат можно исправить; ошибочную последнюю запись — отменить.
К каждому голу с известным автором можно указать пас партнёра по команде; в истории игр он
показан в скобках («Алихан (Дамир)»), а в профиле считаются ассисты. Старые игры пасов не имеют.

Первую пару выбирает жребий: «Начать матч» открывает шторку с монетой, бросок стартует матч, и
сервер один раз решает, кто отдыхает первым (три команды) или кто начинает с мячом (две команды);
монета только показывает этот результат.

При трёх командах после первой игры проигравшая отдыхает. При первой ничьей
организатор выбирает севшую команду по фактическому результату сулифа; в таблице
остаётся ничья. Далее команда, сыгравшая два раза подряд, отдыхает при любом
результате. При двух командах повторяется одна пара. Шесть минут — ориентир:
живого таймера и автоматической записи результата нет.

Завершение всего матча — отдельное действие в меню «⋯» рядом с «Внести результат» во вкладке «Игры».
Оно открывает существующий опрос фактическим участникам; закрытие оплаты сам матч не завершает.
При завершении без сыгравших опрос не создаётся. Старые матчи сохраняют прежние
правила старта по времени и не получают вымышленную статистику.

Нужна добавочная миграция **`0011_game_statistics.sql` перед новым Worker**.
Проверки и порядок будущего обновления: [игровой протокол](docs/game-statistics-review.md).

## Лента

На главной под задачами и списком матчей стоит «Лента»: отдельные карточки-посты о сыгранных и предстоящих
матчах всех групп человека. Их видят все участники группы; из чужой группы посты не видны.

- **После матча** (при «Завершить встречу»): кто выиграл, герой матча (голы плюс передачи), хет-трик,
  дубль, лучший ассистент, связка, крупный счёт, самая результативная игра, серия побед команды,
  итог в цифрах. Из них публикуются самые заметные, не больше шести; победитель всегда первый.
- **Достижения и вехи**: новый уровень достижения (начиная с бронзы), дебют в группе, голы или
  победы в нескольких матчах подряд. История считается внутри одной группы.
- **Лучший по оценкам**: когда через 72 часа закрывается голосование, пост называет игрока с лучшей
  средней оценкой (не меньше трёх голосов). Кто как голосовал, в ленту не попадает.
- **Перед матчем**: открыта запись, назначены время и поле, собран состав, опубликованы команды.
  После матча или отмены эти посты уходят.

Пост об игроке подписан им самим: фото из Telegram и имя, ниже тип новости и день. Фото берётся из
подписанного initData при входе в мини-апп и хранится в `users.photo_url`; у того, кто ещё не открывал
приложение, вместо фото инициалы. Под каждым постом три реакции: 🔥, 👍 и 👎. У человека одна реакция
на пост: другая заменяет первую, повторное нажатие снимает. Реакции хранятся в `feed_reactions` по
матчу и слоту поста, поэтому не теряются, когда пост переписывается после исправления результата.

Пока на посте нет реакций, под ним одна кнопка «Реакция»; по нажатию она раскрывается в три.
Администратор группы видит на посте «⋯» и может удалить пост для всех (`DELETE /api/feed/:id`).
Удалённые посты помечаются в `feed_hidden` по матчу и слоту и не возвращаются при переписывании.

Нажатие на пост об игроке открывает его спортивный профиль шторкой прямо на главной; остальные
посты ведут в матч. Если у завершённого матча с записанными играми нет постов (он сыгран до
появления ленты или запись не удалась), они создаются при следующем открытии ленты, от старых
матчей к новым, с датой самого матча. Встречи без игровой статистики постов не получают.

Тексты собираются из шаблонов в `packages/core/src/feed.ts`: у каждого сюжета несколько
формулировок в разной манере, выбор зависит от матча и пропускает недавно использованные в группе.
Имена и названия команд стоят только в именительном падеже, о людях пишем в настоящем времени
(пол неизвестен), по имени только хвалим. Посты хранятся в `feed_posts`; исправление результата
после завершения переписывает посты этого матча.

## Травмы

Администратор группы отмечает травму на экране «Игроки»: «Управление» у игрока → «Отметить травму»
(или «Снять травму»), рядом с кнопкой «Сделать организатором». Организаторы и игроки менять отметку не могут.
У травмированного игрока в левом верхнем углу аватара появляется красный крест на белом круге — в списке
игроков, в составе матча и в профиле; скринридер читает «Травма». Отметка принадлежит группе: в другой
команде игрок травмированным не показывается, а в профиле крест виден, если травма отмечена хотя бы в одной
общей со зрителем группе. На запись, составы и рейтинг отметка не влияет. Колонка добавляется миграцией
`0014_injury_status`.

## Переменные

| Имя                  | Где                       | Что                                                    |
| -------------------- | ------------------------- | ------------------------------------------------------ |
| `BOT_TOKEN`          | секрет                    | токен бота от @BotFather                               |

## Деплой (сначала — в тестовой группе)

1. **Бот.** В @BotFather: `/newbot` → токен; `/setprivacy` → Enable.
2. **Cloudflare.**
   ```bash
   cd apps/worker
   pnpm exec wrangler login
   pnpm exec wrangler d1 create fc-altynka          # id вписать в wrangler.jsonc → d1_databases[0].database_id
   pnpm exec wrangler d1 migrations apply fc-altynka --remote
   pnpm exec wrangler secret put BOT_TOKEN
   pnpm exec wrangler secret put WEBHOOK_SECRET
   ```
   В `wrangler.jsonc` → `vars` вписать `BOT_USERNAME`, `MINIAPP_SHORT_NAME`.
   `ADMIN_TG_ID` используется только для переноса роли прежнего владельца в существующей группе;
   глобальных прав в новых группах этот ID не даёт.
3. **Деплой:** из корня `pnpm run deploy` (именно `run`: `pnpm deploy` — встроенная команда pnpm).
   Проверка: `https://<worker>.workers.dev/api/health` → `{"ok":true}`.
4. **Мини-апп.** В @BotFather: `/newapp` → выбрать бота, URL = адрес воркера, short name = `MINIAPP_SHORT_NAME`.
5. **Вебхук и кнопка меню.** Создать `apps/worker/.webhook.env` (он в `.gitignore`, в git не попадёт) с теми же
   значениями, что ушли в `wrangler secret put`:
   ```bash
   BOT_TOKEN='...'
   WEBHOOK_SECRET='...'
   WORKER_URL='https://<worker>.workers.dev'
   ```
   и запустить из корня `apps/worker/scripts/set-webhook.sh`. Токен и секрет не вписывать в сам скрипт.
   В выводе `getWebhookInfo` не должно быть `last_error_message`.
6. **Группа.** Любой администратор Telegram-группы добавляет бота администратором с правом закреплять
   сообщения и отправляет `/bind` от своего личного аккаунта → «Группа привязана ✅» и кнопка команды.
7. **Другие группы.** Повторить шаг 6 в каждой группе. Создаётся отдельная команда; существующая группа,
   открытые матчи и история сохраняются. Повторный `/bind` в том же чате не сбрасывает данные.
   Превращение группы в супергруппу меняет чат только её команды автоматически.

## Несколько независимых команд

Приложение открывается без выбора команды: ленты матчей и задач объединяют все группы человека, а при
нескольких группах карточки помечаются тегом группы. Группа выбирается только при создании матча.
Показываются только команды с подтверждённым членством, без общего каталога групп. Новому участнику нужно впервые открыть
ссылку в своей группе. Одного добавления бота недостаточно для импорта всех участников Telegram.

Матчи, составы, рейтинги, имена в списках, футбольные анкеты, телефоны получателей и подписки на
уведомления принадлежат конкретной команде. Telegram-идентичность, тема и доступность личного чата
общие. Администраторы Telegram управляют только своей командой и могут назначать её организаторов.
Сервер проверяет членство при каждом запросе; чужой ID или пересланная кнопка не дают доступа.

Удаление бота или снятие нужных прав приостанавливает работу команды. После возврата прав и `/bind`
ожидающая синхронизация и будущие уведомления возобновляются с сохранением защиты от повторной доставки.
Вебхук должен принимать `chat_member` и `my_chat_member`; обновлённый `set-webhook.sh` включает их.

### Обновление существующей установки

`0009_multiple_groups.sql` переносит настройки из `users` в существующие `memberships`, сохраняя
идентификаторы команд, матчей и счетов. В новых членствах эти настройки пустые. Старый владелец остаётся
администратором, если Telegram подтверждает этот статус; обычному участнику прежней группы однократно
сохраняется роль организатора. Подтверждённый выход из группы аннулирует неиспользованное право переноса.

Перед production-обновлением сохранить экспорт D1 и версию Worker, приостановить обработку изменений,
применить миграцию, развернуть совместимый Worker и обновить вебхук, затем возобновить работу. Не оставлять
старый Worker принимать изменения между копированием профилей и переключением на новую модель.
Простой возврат старого кода после подключения нескольких групп небезопасен: старый код выбирает первую
группу и пишет в общий профиль. Для отката нужен согласованный снимок кода и базы; после новых записей
потребуется отдельный перенос данных, чтобы их не потерять.

Локальные проверки: `pnpm test`, `pnpm test:migrations` (Node с поддержкой `node:sqlite`), `pnpm typecheck`,
`pnpm build`, `pnpm exec playwright test`. Тест миграции использует только базу SQLite в памяти.
