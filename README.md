# FC Altynka — Telegram-бот + мини-апп

Бот ведёт сбор на игру одним самообновляющимся сообщением в группе: запись кнопкой «Иду», резерв, назначение времени,
составы и счёт. Мини-апп — для деталей, составов, счёта, игровых профилей и оценки матчей.

- Дизайн: `docs/superpowers/specs/2026-11-03-football-sbor-bot-design.md`
- План: `docs/superpowers/plans/2026-11-03-football-sbor-bot.md`
- Текущий интерфейс: [`DESIGN.md`](DESIGN.md), [план переноса Airofit](docs/superpowers/plans/2026-11-04-airofit-app.md).
- Игровые характеристики и анонимные оценки: [правила](docs/superpowers/specs/2026-11-05-player-ratings-design.md), [проверка реализации](docs/player-ratings-review.md).
- Сообщения и команды бота: [сценарии](docs/bot-copy-draft.md), [реализация и доставка](docs/bot-delivery-review.md).

## Структура

| Пакет           | Что внутри                                                                                    |
| --------------- | --------------------------------------------------------------------------------------------- |
| `packages/core` | Чистая логика: очередь и резерв, деление команд, рейтинг игроков, счёт, форматирование, типы API               |
| `apps/worker`   | Cloudflare Worker: вебхук бота (grammY), API (Hono), D1 (Drizzle), Durable Object `EventSync` |
| `apps/miniapp`  | Мини-апп на React + Vite; собирается в `apps/miniapp/dist` и раздаётся тем же Worker'ом       |

```text

    src/
      components/  # общие компоненты, навигация и жесты
      hooks/       # загрузка данных и поведение окон
      lib/         # API, Telegram, платежные ссылки и тема

scripts/           # обслуживание бота и коннекторов

```

## Разработка

```bash
pnpm install
pnpm test          # все тесты
pnpm typecheck     # проверка типов
pnpm build         # сборка мини-аппа
pnpm test:ui       # production-сборка, мобильные экраны и доступность (Playwright/axe)
pnpm test:connectors # локальные тесты Telegram MCP
pnpm check:telegram # диагностика реального бота без отправки сообщений
pnpm bot:profile   # показать план оформления бота без сетевых изменений
pnpm channel:post  # проверить пост для канала новостей; публикация только с --apply
pnpm backup        # бэкап продовой D1 с учебным восстановлением, см. «Бэкапы и восстановление»
```

**CI.** GitHub Actions (`.github/workflows/ci.yml`) на каждый PR и push в `main` запускает две задачи:
«Типы и тесты» (`typecheck`, `test`, `test:migrations`, `test:connectors`) и «Playwright» (`test:ui` в Chromium и
WebKit). В CI Playwright повторяет упавший тест до двух раз: прошедший со второй попытки тест помечается как flaky
в отчёте, а не скрывается. При падении отчёт и трейсы можно скачать в артефакте `playwright-report`. Деплой
из CI не выполняется.

Локально: `cp apps/worker/.dev.vars.example apps/worker/.dev.vars`, затем
`cd apps/worker && pnpm exec wrangler d1 migrations apply fc-altynka --local && pnpm exec wrangler dev`.
Мини-апп в браузере: `pnpm --filter @altynka/miniapp dev` (проксирует `/api` на `localhost:8787`).
Без Telegram мини-апп покажет «Открой мини-апп из Telegram» — это нормально.

В группе бот публикует общие объявления, составы и компактный счёт. Личные уведомления игрок включает в `/settings`
в личке бота или в профиле миниапки. По умолчанию они выключены. Подписчику бот пишет лично, когда открыта запись
на новый матч (с кнопкой «Иду»), назначены или изменились время и поле, матч отменён, он перешёл между основой и
резервом, опубликованы составы (с его командой), до матча два часа, выставлен счёт и можно оценить игру.
Сразу после завершения встречи со статистикой каждый сыгравший подписчик получает личные итоги: свои голы,
передачи, результат коротких игр и уровни достижений, открытые этой встречей.
Объявление о новом матче получают все подписанные участники группы, кроме создателя; рассылка идёт порциями.

Личный чат с ботом — рабочий экран, а не только кнопка запуска: `/start` показывает ближайший матч, место в
очереди, сумму к оплате и состояние уведомлений; записаться и отменить запись можно кнопкой прямо в сообщении.
Кнопки меню перерисовывают то же сообщение, обычный текст без команды открывает меню.
Команды в личке: `/start`, `/matches`, `/payments`, `/settings`, `/help`; организаторам дополнительно `/newmatch`.

Новости проекта выходят в канале [@fc_altynka_news](https://t.me/fc_altynka_news). Пост публикует бот:
`pnpm channel:post <файл>` проверяет текст и ничего не отправляет, с `--apply` публикует. Порядок работы и правила
текста описаны в навыке `.claude/skills/channel-post`, опубликованные посты записываются в
[`docs/channel-posts.md`](docs/channel-posts.md).
Для применения имени, описания, меню и областей команд после обновления обработчиков: `pnpm bot:profile --apply`.
Скрипт не меняет вебхук и аватар. Диагностика `pnpm check:telegram` читает также команды для лички и группы;
пустой default scope сам по себе не означает, что команды не настроены.

Разбор архитектуры, обновление UI, состояние интеграций и ограничения проверки:
[`docs/project-audit.md`](docs/project-audit.md). Визуальные правила: [`DESIGN.md`](DESIGN.md).

## Игровые рейтинги

При входе участник получает предложение пройти анкету из восьми навыков (1–10).
Стартовый рейтинг — среднее ответов; далее учитываются до десяти последних матчей
с достаточным числом оценок. Анкета имеет вес трёх матчей. Один и тот же рейтинг
с точностью до десятых показывается в профиле и используется при делении команд.

Организатор отдельно подтверждает завершение игры и фактических участников.
Им открывается анонимный опрос на 72 часа. Опрос закрывается раньше, если ответили
все участники с аккаунтом (пропустили опрос или оценили и прошли шаг наград, выбрав или пропустив
награды), либо если организатор нажал
«Закрыть опрос» на странице оценки; закрытие необратимо. Пока опрос открыт, организатор
видит, кто ответил, но не сами оценки. После завершения бот один раз зовёт в опрос личным сообщением «Оцени игру»
(с 10:00 до 21:00 по Алматы). Через два часа после доставленного приглашения тем, кто так и не ответил,
уходит одно напоминание «Опрос ждёт тебя» (в тихие часы — в 10:00); после ответа или закрытия опроса — нет. Среднее публикуется при минимум трёх
голосах; оценка игры в целом не влияет на игроков. Список игроков и игровые профили
доступны всем участникам группы. Авторы отдельных чужих оценок API не раскрывает.

### Награды матча

В том же опросе, после оценок игроков и перед оценкой матча, участник выбирает пять наград: MVP матча,
лучший нападающий, полузащитник, защитник и вратарь. Позиция из профиля выбор не ограничивает: любую
награду может получить любой сыгравший участник с аккаунтом (гостей в опросе нет). За себя голосовать
нельзя, любую награду можно пропустить, одного игрока можно выбрать на несколько наград.

В шаге оценки игрока и в списке выбора награды видна его результативность за матч по записанным играм:
голы, пасы (если их записывали), сыгранные игры и победы, ничьи, поражения. Без статистики игр строки нет.

Кто отправил оценки без шага наград (старая версия мини-аппа), пока опрос открыт, видит на странице
оценки карточку «Выбери лучших игроков матча»: только пять шагов наград и сводка выбора. Ответ
дополняется один раз через `POST /api/events/:id/review/awards` (`awards` или `skipped: true`), оценки
не меняются. Пока такой участник не прошёл шаг наград, опрос не закрывается досрочно, а организатор
видит у него «Ждём награды».

Побеждает тот, у кого больше голосов. При равенстве побеждает игрок с более высокой средней оценкой
за этот матч; если и она равна, награду получают все равные, и она идёт в счёт каждому. Награда
присуждается, только если у лидера не меньше двух голосов. Итоги открываются при закрытии голосования
вместе со средними оценками; число голосов видно только у победителя, раскладку голосов API не отдаёт.
Награды не влияют на рейтинг. Победители нигде не хранятся: `awardWinners` в `packages/core` считает
их при чтении по таблице `award_votes`, одинаково для матча, ленты, профиля и таблицы лидеров.

В профиле под статистикой стоит счётчик MVP и выигранные награды по позициям; в «Статистике» есть
вкладка «MVP». Достижения «MVP» (1, 3, 5, 10, 20, 35, 50 наград) и «Лучший на позиции»
(1, 5, 10, 25, 50, 75, 100) считают награды во всех матчах с опросом, в том числе без статистики игр.

**Поздравление.** Когда опрос закрывается (по сроку или досрочно), каждый победитель получает от бота
одно личное сообщение на матч, даже если наград несколько: заголовок без рода («MVP матча — это ты»),
число голосов, цифры за матч по записанным играм и прогресс по лестнице «MVP» или «Лучший на позиции»
(новый уровень или сколько осталось до следующего). Сообщение уходит с 10:00 до 21:00 по Алматы; позже
суток после закрытия опроса не отправляется. Его отправляет объект матча `EventSync`
(`AutomaticNotifications`): к сроку закрытия он просыпается сам, а досрочное закрытие будит его
через `sync.request`. Обычные фильтры личных сообщений (уведомления включены, личка доступна, участник
группы) действуют и здесь; в группу поздравление не дублируется.

**Корона.** Действующий MVP группы — победитель MVP последнего закрытого и не отменённого матча этой
группы, где MVP присуждён (`reigningMvps` в `domain/awards.ts`, просмотр не дальше десяти таких матчей).
Корона переходит к следующему MVP; матч без присуждённого MVP её не забирает, общий MVP коронует всех.
Флаг `reigningMvp` приходит в списке игроков (по группе), в составе матча и в профиле (если корона есть
хотя бы в одной общей со зрителем группе).

Для наград нужна миграция `0018_match_awards.sql` **перед деплоем Worker**, для поста «Церемония» —
`0019_feed_payload.sql` (колонка `feed_posts.payload_json`), тоже до деплоя Worker.

Для включения нужна миграция `0008_player_ratings.sql` **перед деплоем Worker**.
Она сохраняет прежние уровни и помечает существующие матчи как не имеющие опросов.
Следующие матчи включают опросы автоматически. Пользователи без анкеты получают
прежний уровень как предварительный. Опубликованные составы не меняются вслед
за пересчётом рейтинга. Ручное изменение вычисляемого уровня удалено.

## Игровая статистика

В интерфейсе **матч** — это весь сбор (запись, составы, оплата), а **игра N** — короткая
игра внутри него. Слово «встреча» в приложении не используется.

Новые матчи начинаются по кнопке организатора **«Начать матч»** во вкладке
«Составы». До нажатия доступны запись, гости, балансировка и ручные перестановки,
даже если назначенное время уже наступило. Старт фиксирует команды на весь матч
и случайно выбирает первую пару. После старта менять участников и составы нельзя.

Во вкладке «Игры» организатор после каждой короткой игры записывает результат и
забивших. Можно указать несколько голов одного игрока или гостя (кнопка «… ещё раз» повторяет предыдущего автора), а неизвестного
автора дополнить позже. Приложение считает таблицу (3/1/0 очка), мячи, разницу
голов и бомбардиров. Результат можно исправить; ошибочную последнюю запись — отменить.
К каждому голу с известным автором можно указать пас партнёра по команде; в истории игр он
показан в скобках («Алихан (Дамир)»), а в профиле считаются ассисты. Карточка лидеров матча
переключается между «Голы» (бомбардиры) и «Пасы» (ассистенты). Старые игры пасов не имеют.

Первую пару выбирает жребий: «Начать матч» открывает шторку с монетой, бросок стартует матч, и
сервер один раз решает, кто отдыхает первым (три команды) или кто начинает с мячом (две команды);
монета только показывает этот результат.

При трёх командах после первой игры проигравшая отдыхает. При первой ничьей
организатор выбирает севшую команду по фактическому результату сулифа; в таблице
остаётся ничья. Далее команда, сыгравшая два раза подряд, отдыхает при любом
результате. При двух командах повторяется одна пара. Шесть минут — ориентир:
живого таймера и автоматической записи результата нет.

Завершение всего матча — отдельное действие в меню «⋯» рядом с «Внести результат» во вкладке «Игры».
Оно открывает существующий опрос фактическим участникам; закрытие оплаты сам матч не завершает.
При завершении без сыгравших опрос не создаётся. Старые матчи сохраняют прежние
правила старта по времени и не получают вымышленную статистику.

Нужна добавочная миграция **`0011_game_statistics.sql` перед новым Worker**.
Проверки и порядок будущего обновления: [игровой протокол](docs/game-statistics-review.md).

### Страница «Статистика»

Центральная кнопка дока у всех участников открывает «Меню»: «Создать матч» (только у тех, кто может создавать), «Статистика», «Игроки», «Площадки».
«Статистика» (`/stats`, `GET /api/statistics`) — таблица игроков по голам, пасам, сумме «гол+пас», играм и победам. Считается по тем же
сохранённым протоколам, что и профиль игрока (`domain/leaderboard.ts`), новых таблиц нет. Ответ приходит по группам смотрящего; фильтр
«Все игроки» складывает человека по общим группам на клиенте (`mergeLeaderboard` в `packages/core`). В списке только действующие участники
группы, сыгравшие хотя бы одну игру; гости без аккаунта не показываются. Пасы начали записывать позже голов: у игрока без таких игр стоит «—».

## Лента

На главной под задачами и списком матчей стоит «Лента»: отдельные карточки-посты о сыгранных и предстоящих
матчах всех групп человека. Их видят все участники группы; из чужой группы посты не видны.

- **После матча** (при «Завершить встречу»): кто выиграл, герой матча (голы плюс передачи), хет-трик,
  дубль, лучший ассистент, связка, крупный счёт, самая результативная игра, серия побед команды,
  итог в цифрах. Из них публикуются самые заметные, не больше шести; победитель всегда первый.
- **Достижения и вехи**: новый уровень достижения (начиная с бронзы), дебют в группе, голы или
  победы в нескольких матчах подряд. История считается внутри одной группы.
- **Лучший по оценкам**: когда через 72 часа закрывается голосование, пост называет игрока с лучшей
  средней оценкой (не меньше трёх голосов). Кто как голосовал, в ленту не попадает.
- **Церемония**: в тот же момент выходит один пост с каруселью карточек, по карточке на каждого победителя
  каждой награды: награда, титул («Гроза ворот»), свой текст из шаблонов этой награды, цифры за матч и
  число голосов. Тексты и цифры фиксируются при записи (`feed_posts.payload_json`), имя и фото берутся при
  чтении. Если MVP присуждён, церемония заменяет «Лучший по оценкам». Церемония идёт от матча, а не от MVP, даже
  если в старой записи автором сохранён MVP.
  Матчи, у которых уже есть старый пост «Награды матча» (вид `awards`), второй пост не получают; старые
  посты остаются текстом. Исправление результата матча церемонию не переписывает.
- **Перед матчем**: открыта запись, назначены время и поле, собран состав, опубликованы команды.
  После матча или отмены эти посты уходят.

Пост об игроке подписан им самим: фото из Telegram и имя, ниже тип новости и день. Фото берётся из
подписанного initData при входе в мини-апп и хранится в `users.photo_url`; у того, кто ещё не открывал
приложение, вместо фото инициалы. Под каждым постом три реакции: 🔥, 👍 и 👎. У человека одна реакция
на пост: другая заменяет первую, повторное нажатие снимает. Реакции хранятся в `feed_reactions` по
матчу и слоту поста, поэтому не теряются, когда пост переписывается после исправления результата.

Пока на посте нет реакций, под ним одна кнопка «Реакция»; по нажатию она раскрывается в три.
Администратор группы видит на посте «⋯» и может удалить пост для всех (`DELETE /api/feed/:id`).
Удалённые посты помечаются в `feed_hidden` по матчу и слоту и не возвращаются при переписывании.

Нажатие на пост об игроке открывает его спортивный профиль шторкой прямо на главной; остальные
посты ведут в матч. Если у завершённого матча с записанными играми нет постов (он сыгран до
появления ленты или запись не удалась), они создаются при следующем открытии ленты, от старых
матчей к новым, с датой самого матча. Встречи без игровой статистики постов не получают.

Тексты собираются из шаблонов в `packages/core/src/feed.ts`: у каждого сюжета несколько
формулировок в разной манере, выбор зависит от матча и пропускает недавно использованные в группе.
Имена и названия команд стоят только в именительном падеже, о людях пишем в настоящем времени
(пол неизвестен), по имени только хвалим. Посты хранятся в `feed_posts`; исправление результата
после завершения переписывает посты этого матча.

## Календарь доступности

Игрок один раз отмечает, когда может играть: профиль → «Когда могу играть» (нижний лист поверх профиля, отметки сохраняются сразу). Календарь общий для всех групп человека.

- Календарь — **текущая неделя, с понедельника по воскресенье**. Отмечать можно дни с сегодняшнего по воскресенье; прошедшие дни недели видны с прежней отметкой, но недоступны. Следующая неделя открывается в понедельник. Постоянного графика по дням недели нет: у игрока один календарь, который он обновляет раз в неделю.
- Три состояния дня: не указано, «Могу», «Не могу». «Могу» всегда со временем: одно или несколько окон — до 12:00, 12:00–15:00, 15:00–18:00, 18:00–20:00, 20:00–22:00, после 22:00 — или «Весь день». Пока время не выбрано, отметка не сохраняется.
- **Уведомление о новом матче** не приходит тем, у кого на дату матча стоит «Не могу». Пустой календарь ничего не меняет: человек получает сообщение как раньше. Кто отметил «Могу», видит в сообщении строку об этом. Матч всё равно виден в группе и в мини-апп, записаться можно.
- **Напоминание по понедельникам**: с 9:00 до 13:00 по Алматы бот один раз пишет в личный чат «Когда сможешь играть на этой неделе?» с кнопкой календаря. Получают те, у кого включены уведомления и есть группа; у кого вся неделя уже отмечена, сообщение не приходит. Рассылка идёт порциями из крона `*/5`.
- **Напоминание в мини-апп**: главная показывает лист «Когда сможешь играть?» тем, кто с понедельника (по Алматы) ещё ничего не отмечал и у кого среди оставшихся дней недели есть пустые. Кто отметил хотя бы один день на этой неделе, листа не видит до следующего понедельника, даже когда в календаре появляется новый пустой день. «Позже» или переход в календарь тоже закрывают лист до понедельника (запоминается на устройстве). Пока не пройдена анкета навыков, лист не показывается.
- Фильтр смотрит только на дату: при создании у матча ещё нет времени. Окна времени нужны организатору.
- **Организатор** в листе «Новый матч» выбирает дату только на ленте из 14 дней (отдельного поля даты нет, матч создаётся не дальше двух недель): она листается, под каждым днём — сколько человек может (игроки отмечают только текущую неделю, поэтому отметки есть до воскресенья). Под лентой строка «Могут играть · N из M»; «Кто может» раскрывает полную статистику: кто может в каждое из окон времени, кто не может и сколько не отметили. Игроки чужих отметок не видят.

API: `GET /api/availability`, `PUT /api/availability/days/:date`, `GET /api/availability/summary?communityId=` (организатор). Отметки хранятся в `availability_days` (миграция `0016_availability`, её нужно применить до деплоя Worker). Таблица `availability_weekly` из той же миграции осталась от убранного обычного графика и не используется.

## Формат матча и площадки

При назначении матча организатор выбирает время, длительность, **формат** и площадку.

- **Формат** задаёт размер основы: «5×5» — 10 игроков, «6×6» — 12, «5×5×5» — 15, «6×6×6» — 18. Остальные записавшиеся
  стоят в резерве. Пока формат не выбран вручную, длительность подсказывает привычный вариант: час — две команды,
  два часа — три. У назначенного матча формат меняется только явно; при смене формата основа и резерв
  пересчитываются, игроки получают уведомления о переходе. До назначения матча основа — 10 человек.
- **Площадки** принадлежат группе (таблица `venues`). В листе «Место проведения» организатор выбирает поле из
  списка, добавляет новое («Добавить площадку»: название, адрес, ссылка на карту, цена за час — всё, кроме названия,
  необязательно) или удаляет ненужное. Название уникально в группе. Матч хранит название площадки
  (`events.place`), поэтому удаление площадки не меняет уже назначенные и прошедшие матчи. Список видят все
  участники группы, менять его может организатор. API: `GET/POST /api/venues?communityId=`, `PATCH/DELETE /api/venues/:id`.
- **Страница «Площадки»** (`/venues`, открывается из меню): все участники видят адрес, ссылку на карту и цену за час по каждой
  своей группе. Организатор группы там же добавляет, правит и удаляет площадки. Переименование, как и удаление,
  не меняет матчи, где площадка уже указана.
- **Гости.** Игрок может привести на один матч не больше трёх друзей (`MAX_GUESTS_PER_PLAYER` в
  `packages/core/src/queue.ts`); четвёртый получает `409 guest_limit`, а мини-апп объясняет почему. Удалённый гость
  освобождает место. Организатор записывает гостей без ограничения: так в состав попадают люди без Telegram.

## Травмы

Администратор группы отмечает травму на экране «Игроки»: «Управление» у игрока → «Отметить травму»
(или «Снять травму»), рядом с кнопкой «Сделать организатором». Организаторы и игроки менять отметку не могут.
У травмированного игрока в левом верхнем углу аватара появляется красный крест на белом круге — в списке
игроков, в составе матча и в профиле; скринридер читает «Травма». Отметка принадлежит группе: в другой
команде игрок травмированным не показывается, а в профиле крест виден, если травма отмечена хотя бы в одной
общей со зрителем группе. На запись, составы и рейтинг отметка не влияет. Колонка добавляется миграцией
`0014_injury_status`.

## Защита API

- **Лимиты запросов** — привязки Rate Limiting в `wrangler.jsonc`, ключ — Telegram ID (`tg:<id>`): `API_LIMITER` —
  300 запросов в минуту на человека, `WRITE_LIMITER` — 60 изменений в минуту (каждое спрашивает Telegram о членстве).
  Сверх лимита — `429 rate_limited` до любой записи в базу. Тело запроса — не больше 64 КБ (`413 too_large`; если Cloudflare передал тело без `Content-Length`, лимит
  срабатывает при чтении, а неподписанный запрос получает 401, не читая тело).
- **Проверка членства.** Изменения всегда спрашивают Telegram. Чтения (`GET`) доверяют подтверждению не старше
  5 минут (`MEMBERSHIP_CACHE_MS`); выход из группы и смена прав приходят апдейтом `chat_member` и сбрасывают его сразу.
  Если Telegram не отвечает (429, сеть), решает сохранённое активное членство, как в `GET /me`; без него — `503
  telegram_busy` с `Retry-After`.
- **Ошибки.** Необработанная ошибка API — JSON `500 {error:'internal'}` и структурированная строка в логах. Ошибка в
  обработчике бота логируется (`bot_update_failed`) и не роняет вебхук, иначе Telegram повторял бы тот же апдейт;
  на нажатую кнопку бот отвечает «Не получилось. Попробуй ещё раз.».
- **Получатель счёта.** Организатор выбирает получателем себя (номер Kaspi можно вписать прямо в счёте) или участника,
  который сам сохранил номер в профиле. Вписать или поменять номер за другого нельзя: иначе в счёте стояло бы одно имя,
  а кнопки оплаты вели бы на чужой номер. Сервер отвечает `409 receiver_no_phone` / `receiver_phone_locked`, а в
  мини-аппе игроков без номера нет в списке «Кто заплатил за поле».
- **Секреты** (`WEBHOOK_SECRET`, подпись initData) сравниваются за постоянное время (`crypto.subtle.timingSafeEqual`).
- **Заголовки статики** — `apps/miniapp/public/_headers`: CSP, `nosniff`, `Referrer-Policy`, `Permissions-Policy`.
  `vite preview` отдаёт те же заголовки, а Playwright падает на любом нарушении CSP, так что новый внешний ресурс
  нужно добавить в политику.
- **Наблюдаемость** — логи и трейсы Workers включены в `wrangler.jsonc` (`observability`).
- **Алерты** (`src/ops/alerts.ts`). Необработанные ошибки API, упавшие апдейты бота и сбои задач крона
  записываются в `ops_incidents`. Крон раз в 5 минут присылает в личку `ALERT_CHAT_ID` одну сводку: сколько сбоев
  каждого вида и текст последнего, плюс новую ошибку вебхука из `getWebhookInfo` или очередь от 20 необработанных
  апдейтов. Сводки приходят не чаще раза в 30 минут, а сбои между ними попадают в следующую. Если Telegram не принял
  сводку, она уйдёт следующим прогоном. Записи старше 14 дней удаляются. Получатель должен хоть раз написать боту
  `/start`. Пустой `ALERT_CHAT_ID` выключает отправку.
- **Ошибки мини-аппа.** Упавший экран показывает «Что-то сломалось» с кнопкой перезагрузки вместо белой страницы, а
  нижняя панель остаётся рабочей: переход на другой экран снимает ошибку. Ленивый экран, который не загрузился после
  деплоя (старая вкладка), один раз перезагружается сам. Ошибки рендера, `error` и `unhandledrejection` уходят в
  `POST /api/client-errors` (подпись Telegram, общие лимиты) и попадают в ту же сводку алертов как «Мини-апп». Стек
  пишется только в логи Cloudflare. Обрывы связи, отменённые запросы и ответы API 4xx не отправляются, одна и та же
  ошибка уходит один раз за сессию, всего не больше 5 отчётов.
- **Поддержка.** Профиль → «Системные настройки» → «Сообщить о проблеме»: текст (до 1000 знаков) уходит
  `POST /api/feedback` и сразу пересылается ботом в личку `FEEDBACK_CHAT_ID` с именем и ссылкой на автора, его
  группами, экраном и версией. Не чаще раза в 30 секунд от человека (`429 too_often`); в базе текст не хранится.
  Внизу системных настроек — «Версия a1b2c3d · 25 нояб.»: коммит сборки (`+`, если собрано с незакоммиченными
  правками) из `vite.config.ts`. Та же версия уходит в отчёты об ошибках мини-аппа и в сообщения о проблемах.
- **Health check.** `GET /api/health` отвечает `503`, если D1 недоступна (`db_unavailable`) или крон не отрабатывал
  дольше 15 минут (`cron_stale`). Остановку всего Worker сам Worker сообщить не может, поэтому `/api/health`
  проверяет внешний монитор (Cloudflare Health Checks, UptimeRobot и т. п.) раз в 1–5 минут и уведомляет при
  нескольких неудачах подряд.
- **Размещение** — Worker выполняется во Франкфурте (`placement: { mode: "targeted", region: "aws:eu-central-1" }`),
  рядом с D1 (EEUR) и Bot API Telegram, а не в Алматы, куда приходят запросы игроков: так страница матча с
  десятками обращений к базе открывается вдвое быстрее. Smart Placement здесь не срабатывает — почти весь трафик
  из одного места. Замеры: `docs/security-hardening-deployment.md`.

## Деплой (сначала — в тестовой группе)

1. **Бот.** В @BotFather: `/newbot` → токен; `/setprivacy` → Enable.
2. **Cloudflare.**
   ```bash
   cd apps/worker
   pnpm exec wrangler login
   pnpm exec wrangler d1 create fc-altynka          # id вписать в wrangler.jsonc → d1_databases[0].database_id
   pnpm exec wrangler d1 migrations apply fc-altynka --remote
   pnpm exec wrangler secret put BOT_TOKEN
   pnpm exec wrangler secret put WEBHOOK_SECRET
   ```
   В `wrangler.jsonc` → `vars` вписать `BOT_USERNAME`, `MINIAPP_SHORT_NAME`.
   `ADMIN_TG_ID` используется только для переноса роли прежнего владельца в существующей группе;
   глобальных прав в новых группах этот ID не даёт.
3. **Деплой:** из корня `pnpm run deploy` (именно `run`: `pnpm deploy` — встроенная команда pnpm).
   Проверка: `https://<worker>.workers.dev/api/health` → `{"ok":true}`.
4. **Мини-апп.** В @BotFather: `/newapp` → выбрать бота, URL = адрес воркера, short name = `MINIAPP_SHORT_NAME`.
5. **Вебхук и кнопка меню.** Создать `apps/worker/.webhook.env` (он в `.gitignore`, в git не попадёт) с теми же
   значениями, что ушли в `wrangler secret put`:
   ```bash
   BOT_TOKEN='...'
   WEBHOOK_SECRET='...'
   WORKER_URL='https://<worker>.workers.dev'
   ```
   и запустить из корня `apps/worker/scripts/set-webhook.sh`. Токен и секрет не вписывать в сам скрипт.
   В выводе `getWebhookInfo` не должно быть `last_error_message`.
6. **Группа.** Любой администратор Telegram-группы добавляет бота администратором с правом закреплять
   сообщения и отправляет `/bind` от своего личного аккаунта → «Группа привязана ✅» и кнопка команды.
7. **Другие группы.** Повторить шаг 6 в каждой группе. Создаётся отдельная команда; существующая группа,
   открытые матчи и история сохраняются. Повторный `/bind` в том же чате не сбрасывает данные.
   Превращение группы в супергруппу меняет чат только её команды автоматически.

## Политика конфиденциальности

Статическая страница `apps/miniapp/public/privacy.html`, адрес `/privacy.html` у Worker. Открывается из профиля
(«Системные настройки» → «Политика конфиденциальности») и по ссылке в профиле бота в @BotFather. Текст описывает
то, что реально хранится в D1 и кто это видит. Новая таблица или поле с данными о людях, новое место хранения или
новый получатель данных — повод обновить страницу и дату редакции и написать об этом в @fc_altynka_news.

### Удаление данных

Профиль → «Системные настройки» → «Удалить мои данные» (`DELETE /api/me` с `{ "confirm": "delete" }`,
`domain/privacy.ts`, дизайн — `docs/superpowers/specs/2026-11-24-delete-my-data-design.md`). Профиль обезличивается
(«Удалённый игрок», `tg_id = -id`, `deleted_at`), повторный вход того же Telegram-аккаунта создаёт новый пустой
профиль. Удаляются анкета, календарь, реакции, посты ленты о человеке; будущие записи отменяются через обычный
выход из очереди; членства выключаются. Имя вычищается из снимков: `match_participants`, `roster_json`,
`game_state_json` и текстов оставшихся постов (целыми словами). Прошедшие матчи, статистика, строки счетов и
анонимные оценки остаются. Новые посты о человеке после удаления не пишутся. Запрещено, пока человек — получатель
открытого счёта (`409 receiver_open_bill`).

## Staging

Отдельная копия для проверки релиза до прода: Worker `fc-altynka-staging`, своя D1 `fc-altynka-staging`, свой
тестовый бот и тестовая группа. Код и сборка мини-аппа те же, отличаются только привязки (`env.staging` в
`wrangler.jsonc`). Алерты staging выключены (`ALERT_CHAT_ID` пуст). Реальных игроков и их данных в staging нет:
это пустая база, которую наполняет тестовая группа.

Релиз идёт так: ветка → CI зелёный → `pnpm release --staging` → проверка руками в тестовой группе → мерж →
`pnpm release`.

```bash
pnpm release --staging         # миграции staging D1 + деплой staging Worker + проверка, с любой ветки
pnpm release                   # прод: только из чистого main с зелёным CI, бэкап перед миграциями
pnpm db:migrate:staging        # по отдельности: миграции в staging D1
pnpm run deploy:staging        #                 сборка мини-аппа + деплой staging Worker
```

`pnpm release` (`scripts/release.mjs`) по шагам:

1. Прод: ветка `main`, нет незакоммиченных правок, локальный `main` совпадает с `origin/main`, CI этого коммита
   завершён успешно (`--skip-ci` пропускает только эту проверку). Staging: любая ветка, без этих проверок.
2. Запоминает текущую версию Worker.
3. Если есть новые миграции: на проде `pnpm backup` (с учебным восстановлением), затем `migrations apply`.
4. Деплой (`pnpm run deploy` / `deploy:staging`).
5. Проверка: `/api/health` отвечает `ok`, у вебхука нет ошибки новее деплоя (токен из `.webhook.env` /
   `.webhook.staging.env`; если файла нет или Telegram недоступен, вебхук не проверяется).
6. Проверка не прошла → `wrangler rollback` на версию из шага 2 и ошибка. Миграции при этом остаются применёнными.

Отчёт каждого релиза (коммит, версии, миграции, бэкап, результат) — `artifacts/deploy/releases/*.json`.

Настройка с нуля (один раз):

1. @BotFather: `/newbot` → тестовый бот; `/setprivacy` → Enable.
2. Создать `apps/worker/.webhook.staging.env` (в git не попадает):
   ```bash
   BOT_TOKEN='...'
   WEBHOOK_SECRET='...'          # openssl rand -hex 32
   WORKER_URL='https://fc-altynka-staging.<you>.workers.dev'
   ```
3. Секреты: `wrangler secret put BOT_TOKEN --env staging` и `wrangler secret put WEBHOOK_SECRET --env staging`
   (в `apps/worker`) с теми же значениями.
4. В `wrangler.jsonc` → `env.staging.vars` вписать `BOT_USERNAME` и `MINIAPP_SHORT_NAME`, затем `pnpm run deploy:staging`.
5. @BotFather: `/newapp` → тестовый бот, URL = адрес staging Worker, short name = `MINIAPP_SHORT_NAME`.
6. `apps/worker/scripts/set-webhook.sh staging` — вебхук и кнопка меню тестового бота.
7. Тестовая группа: добавить бота администратором с правом закреплять сообщения и отправить `/bind`.

## Бэкапы и восстановление

Два уровня защиты, оба бесплатные:

- **D1 Time Travel**: откат базы на любую минуту за последние 7 дней (бесплатный план Workers; на Paid — 30).
  Работает сам, настраивать нечего. Подходит, когда данные испортил релиз или ошибочная операция.
- **`pnpm backup`**: экспорт продовой базы в `artifacts/deploy/backups/` (в git не попадает). Запускать перед каждым
  релизом с миграцией и вообще перед любым рискованным действием с продом. Экспорт на несколько секунд блокирует
  запросы к D1, так что не во время матча. Скрипт пишет два файла:
  - `<время>.sql` — сырой `wrangler d1 export`. **Залить его обратно в D1 нельзя**: строки таблиц там идут раньше
    таблиц, на которые они ссылаются, и D1 падает с `no such table: main.users`;
  - `<время>.restore.sql` — тот же дамп в порядке, который D1 принимает: таблицы и индексы, затем строки (родители
    раньше детей), затем триггеры (иначе `AFTER INSERT` размножили бы строки).

  После экспорта скрипт проверяет дамп (обязательные таблицы, внешние ключи), заливает `.restore.sql` в одноразовую
  локальную D1 и сверяет число строк в каждой таблице. Если что-то не сошлось, команда завершится ошибкой.
  После успешной проверки остаются 10 последних бэкапов (`KEEP_BACKUPS`), более старые пары файлов удаляются:
  так политика конфиденциальности может обещать, что удалённые данные со временем исчезают и из копий.

**Откат через Time Travel** (база остаётся той же, Worker передеплоивать не нужно):

```bash
cd apps/worker
pnpm exec wrangler d1 time-travel info fc-altynka                                  # текущая закладка — запиши её
pnpm exec wrangler d1 time-travel restore fc-altynka --timestamp=2026-11-24T15:00:00+05:00
```

Восстановление само обратимо: команда печатает закладку состояния до отката, и к нему можно вернуться через
`--bookmark=…`.

**Восстановление из файла** (база удалена или нужное состояние старше 7 дней):

```bash
cd apps/worker
pnpm exec wrangler d1 create fc-altynka-restore        # новый id вписать в wrangler.jsonc → d1_databases[0].database_id
pnpm exec wrangler d1 execute fc-altynka --remote --file=../../artifacts/deploy/backups/<время>.restore.sql
pnpm exec wrangler d1 migrations list fc-altynka --remote   # все миграции уже применены: d1_migrations в дампе
cd ../.. && pnpm run deploy                            # Worker начинает работать с восстановленной базой
```

Проверить после восстановления: `/api/health`, `pnpm check:telegram`, открыть мини-апп и ближайший матч.

## Любимый клуб

Игрок выбирает любимый клуб или сборную: «Профиль» → «Настройка профиля» → «Любимый клуб» (шторка с вкладками «Клубы | Сборные», чипами лиг и строкой «Без клуба»). Выбор меняет оформление у самого игрока: клубный акцентный цвет, узор и крупная эмблема в шапке экрана, маленькая эмблема у заголовка. Игроки общих групп видят клуб только в карточке его профиля: она окрашена в цвет клуба, в углу эмблема. Клуб не влияет на составы, ленту, статистику и сообщения бота. Без клуба приложение выглядит как раньше. Неизвестный id клуба (например, убранный из каталога) считается «без клуба». «Удалить мои данные» сбрасывает выбор на сервере и в кэше устройства. Правила оформления: [`DESIGN.md`](DESIGN.md), «Favourite club»; решения: [спека](docs/superpowers/specs/2026-11-25-club-themes-design.md).

Как добавить клуб:

1. Запись в `CLUBS` в `packages/core/src/clubs.ts`: `id` (латинский слаг), название, лига (у сборных её нет), цвета для двух тем, материал карточки и узор. Порядок записей внутри лиги — порядок плиток.
2. Файл эмблемы `apps/miniapp/public/clubs/<id>.svg`, не больше 30 КБ, только свой (эмблемы не грузятся со сторонних сайтов, CSP не меняется). Нет приличного SVG — временная заглушка-щит под тем же именем.
3. `pnpm test`: `packages/core/test/clubs.test.ts` проверяет уникальность id и контраст в обеих темах, `apps/miniapp/test/clubCrests.test.ts` — наличие файла эмблемы и его размер. Контраст (`onAccent` на `accent`, `accentInk` на фоне темы, текст материала на его цвете) — не меньше 4,5:1. Новый клуб с плохими цветами тест не пропустит.
4. Узор: `stripes` (вертикальные полосы), `hoops` (горизонтальные обручи), `halves` (равные вертикальные доли: две половины или три полосы флага) и `solid` — у `solid` рисуется только `colors[0]`, поэтому в нём ровно один цвет (это проверяет тест). Прозрачность узора в шапке считается сама (`clubVariables`): не выше 0,55 в тёмной теме и 0,3 в светлой, и ниже, если иначе текст и подсказка страницы на каком-то цвете узора дадут меньше 4,5:1; светлый узор в тёмной теме и насыщенный в светлой поэтому бледнее. Новый вид узора добавляется только в код: функция `clubPatternCss` в `apps/miniapp/src/lib/clubTheme.ts` и тип узора в `clubs.ts`.
5. Новая лига: добавить её в `CLUB_LEAGUES` и `CLUB_LEAGUE_LABEL`. Миграция не нужна, значения в БД не ограничены.

Проверки интерфейса: `tests/ui/club-theme.spec.ts` (выбор клуба; axe на главной, в профиле и на матче для Барселоны, Реала, Кайрата и Ювентуса в обеих темах; расчёт контраста подзаголовка матча над узором для Реала в тёмной и Ювентуса в светлой; повышенная контрастность; шторка на 320 px; чужой профиль; «без клуба»); скриншоты складываются в `artifacts/ui/club-*.png`.

## Несколько независимых команд

Приложение открывается без выбора команды: ленты матчей и задач объединяют все группы человека, а при
нескольких группах карточки помечаются тегом группы. Группа выбирается только при создании матча.
Показываются только команды с подтверждённым членством, без общего каталога групп. Новому участнику нужно впервые открыть
ссылку в своей группе. Одного добавления бота недостаточно для импорта всех участников Telegram.

Матчи, составы, счета, роль, уровень и отметка о травме принадлежат конкретной команде. Профиль общий
для всех групп человека (миграция `0010_unified_profile`): Telegram-идентичность, имя, фото, позиция и нога,
анкета навыков и рейтинг, номер Kaspi, тема, подписка на уведомления и доступность личного чата. Администраторы Telegram управляют только своей командой и могут назначать её организаторов.
Сервер проверяет членство при каждом запросе; чужой ID или пересланная кнопка не дают доступа.

Удаление бота или снятие нужных прав приостанавливает работу команды. После возврата прав и `/bind`
ожидающая синхронизация и будущие уведомления возобновляются с сохранением защиты от повторной доставки.
Вебхук должен принимать `chat_member` и `my_chat_member`; обновлённый `set-webhook.sh` включает их.

### Обновление существующей установки

`0009_multiple_groups.sql` переносит настройки из `users` в существующие `memberships`, сохраняя
идентификаторы команд, матчей и счетов. В новых членствах эти настройки пустые. Старый владелец остаётся
администратором, если Telegram подтверждает этот статус; обычному участнику прежней группы однократно
сохраняется роль организатора. Подтверждённый выход из группы аннулирует неиспользованное право переноса.

Перед production-обновлением сохранить бэкап (`pnpm backup`) и версию Worker, приостановить обработку изменений,
применить миграцию, развернуть совместимый Worker и обновить вебхук, затем возобновить работу. Не оставлять
старый Worker принимать изменения между копированием профилей и переключением на новую модель.
Простой возврат старого кода после подключения нескольких групп небезопасен: старый код выбирает первую
группу и пишет в общий профиль. Для отката нужен согласованный снимок кода и базы; после новых записей
потребуется отдельный перенос данных, чтобы их не потерять.

Локальные проверки: `pnpm test`, `pnpm test:migrations` (Node с поддержкой `node:sqlite`), `pnpm typecheck`,
`pnpm build`, `pnpm exec playwright test`. Тест миграции использует только базу SQLite в памяти.
