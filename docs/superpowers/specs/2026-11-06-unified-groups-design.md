# Несколько групп без «выбранной команды»

Статус: черновик на согласование, 2026-11-06. Прошёл проверку исполнителем. Заменяет разделы «Участники и профили»,
«Определение текущей команды» и «Интерфейс» из
`2026-11-06-multiple-groups-design.md`. Подключение групп (`/bind`), границы доступа
к матчам и счетам, права администраторов и организаторов внутри группы из того
документа остаются в силе.

## Зачем

Codex сделал так, что приложение начинается с выбора команды. Без выбранной команды
ничего не работает, а человек, у которого нет групп с ботом, дальше экрана
«Подключи свою команду» не проходит. Плашка «Сменить» видна даже тем, у кого
команда одна. В «Новом матче» есть поле «Группа» с единственным вариантом.

Пользователь хочет другую модель: **приложение принадлежит человеку, а группы
нужны только для того, чтобы привязать игру**. Войти может любой. Создать матч
можно только в группе, куда добавлен бот и где человек организатор. Если группа
одна, человек вообще не должен видеть, что групп может быть несколько.

## Цели

1. Войти может любой пользователь Telegram, даже без групп. Он видит свой профиль
   и пустую ленту с подсказкой, как подключить бота к группе.
2. Режима «текущей команды» и переключателя больше нет. «Главная», «Матчи» и
   «Задачи» показывают данные всех подтверждённых групп человека в одной ленте.
3. Профиль у человека один: имя, Kaspi, позиция, рабочая нога, уведомления,
   самооценка навыков.
4. Рейтинг у человека один. Он считается по матчам из всех групп.
5. Экран «Игроки» разбит на разделы по группам.
6. В «Новом матче» поле «Группа» показывается, только если человек организатор
   больше чем в одной группе. Вид: список, по строке на группу, с радиокнопкой
   (макет 2Б из обсуждения).
7. С одной группой приложение выглядит как до появления мультигрупп: без подписей
   групп, без выбора, без плашки.

## Не входит в работу

- Каталог чужих групп, вступление в группу из приложения, приглашения.
- Изменение `/bind` и правил подтверждения членства через Telegram.
- Рейтинг или профиль «по группам» как отдельная опция.
- Глобальный администратор всех групп.

## Анти-цели (результат провален, даже если технически работает)

- Человек с одной группой видит что-то, что намекает на выбор команды.
- Человек без групп получает ошибку или пустой экран без объяснения.
- Матч, счёт, состав или список игроков чужой группы виден тому, кто в ней не состоит.
- Организатор группы A получает права в группе B.
- В уже существующих данных теряются имя, Kaspi или рейтинг человека.

## Решения пользователя

- Вход без команды есть у всех; создавать нельзя, пока бот не добавлен в группу.
- Несколько групп у организатора → выбор группы при создании матча.
- Лента общая, на карточке подпись группы.
- Роль организатора считается отдельно в каждой группе.
- Один общий рейтинг.
- Один общий профиль.
- Экран игроков разбит по группам.
- Выбор группы в «Новом матче» — список по строке.

## Как это работает

### Доступ к данным на сервере

Сейчас `communityMiddleware` требует заголовок `X-Community-Id` для всех маршрутов
после `/communities`. Это уходит. Вместо него:

- Для запросов «про человека» (`/me`, `/me/skills`, `/events`, `/matches`,
  `/notifications`, `/players`, `/players/:userId`) сервер берёт список
  подтверждённых групп человека и отдаёт данные по всем ним.
- Для запросов «про объект» (`/events/:id/*`, `/bills/:id/*`, `/bill-lines/:id`,
  `/signups/:id`) группа определяется по самому объекту, после чего проверяется
  членство человека в ней и его роль **в этой группе**. Права по-прежнему
  вычисляются внутри группы, как в старом документе.
- `POST /events` принимает обязательный `communityId`. Сервер проверяет, что
  человек организатор (или админ Telegram) именно в этой группе.
- `GET /members` и `PATCH /members/:userId` принимают группу явно (параметр
  маршрута или запроса) и проверяют права в ней.

### `/api/me`

Отдаёт общий профиль и рейтинг человека плюс список групп:
`communities: [{ id, title, role }]`. Поле `community` и одиночное `role` уходят.
На клиенте «может создавать матчи» = есть хотя бы одна группа с ролью
organizer или admin.

### Лента

- `GET /events` и `GET /matches` отдают матчи всех групп человека, отсортированные
  как сейчас. Пагинация архива — общая по всем группам.
- Каждый матч в ответе несёт `community: { id, title }`.
- Подпись группы на карточке (над датой, маленький тег с цветной точкой) рисуется,
  только если у человека больше одной группы. Цвет точки стабилен для группы
  (например, по `id` из небольшой палитры).
- Страница матча не меняется. Если групп больше одной, рядом с датой можно показать
  ту же подпись.

### Задачи

`/notifications` собирает долги и задачи по всем группам. Тот же тег группы на
карточке задачи при нескольких группах.

### Создание матча

- Кнопка «Создать матч» в меню показывается всем. Если групп с правом создания нет,
  лист создания показывает объяснение: добавить бота в группу, дать права
  администратора с закреплением, отправить `/bind`, либо попросить организатора
  группы назначить организатором. Текст объяснения различает «у тебя нет групп
  с ботом» и «ты не организатор ни в одной из своих групп».
- Одна доступная группа → поля «Группа» нет, матч создаётся в ней.
- Несколько → список с радиокнопками, по строке на группу. Ничего не выбрано заранее;
  кнопка отправки неактивна, пока группа не выбрана.

### Игроки

`GET /players` отдаёт игроков, сгруппированных по группам человека:
`[{ community: { id, title }, players: PlayerSummaryDto[] }]`. Один и тот же
игрок может встречаться в нескольких разделах с одинаковым рейтингом. При одной
группе заголовок раздела не показывается. Управление ролями для админа Telegram
работает внутри раздела соответствующей группы.

### Профиль

Один набор полей в `users`: `displayName`, `kaspiPhone`, `profileCompletedAt`,
`playingPosition`, `dominantFoot`, `notificationsEnabled`. Строка роли в шапке
профиля («Игрок · FC Altynka») при нескольких группах показывает только роль
без названия группы, либо перечисление групп — на усмотрение исполнителя, главное
без намёка на выбор.

Уникальность имени проверяется среди участников всех групп, где состоит этот
человек, а не по всему боту: незнакомые люди из чужих групп не должны блокировать
друг другу имена, и ответ `name_taken` не должен выдавать людей из невидимых групп.
Внимание: `nameTaken` без `communityId` сейчас не проверяет ничего (`takenNames`
возвращает пустое множество), и на этом же держится разведение имён по умолчанию
в `upsertTgUser` («Данияр 2»); это нужно переписать. Если при вступлении в новую
группу имя совпало с чьим-то там, имя не меняется автоматически. Если админ группы
переименовывает игрока, меняется общее имя, и проверка идёт по всем группам этого
игрока. *(Решение автора документа.)*

Изменение Kaspi пересинхронизирует открытые счета, где человек получатель,
во всех группах (сейчас только в текущей).

Настройка уведомлений в личке бота (`/settings`) становится общей: больше не нужно
выбирать группу.

### Рейтинг

- Самооценка: одна на человека. Таблица `skill_assessments` теряет `community_id`
  (первичный ключ — `user_id`).
- Стартовый уровень без анкеты: среднее `memberships.level` по активным членствам,
  округлённое как сейчас округляется уровень.
- Последние 10 оценённых матчей берутся из всех групп.
- История в профиле — из всех групп, с подписью группы при нескольких группах.
- Чтобы видеть профиль игрока (`/players/:userId`), нужно иметь с ним хотя бы одну
  общую подтверждённую группу. История в чужом профиле показывает только матчи
  групп, общих со смотрящим; само число рейтинга общее.

### Выход из группы

Если человек вышел из группы, его удалили или бот удалён из группы
(`communities.active = false`), *(решение пользователя)*:

- **Рейтинг и собственная история матчей** сохраняются: они считаются по фактическому
  участию (`match_participants`, `player_votes`), а не по текущему членству.
  Рейтинг не меняется от выхода из чата.
- **Неоплаченные долги** остаются в «Задачах» и в `/payments` бота: выборка по
  `bill_lines.user_id`, а не по членству. Отметить оплату по такому счёту можно,
  как и раньше (проверка — что строка принадлежит человеку).
- **Будущие и прошедшие матчи в ленте, список игроков и профили игроков** этой
  группы пропадают: эти выборки идут по подтверждённым членствам.
- В чужом профиле (`/players/:userId`) история показывает только матчи групп, общих
  со смотрящим сейчас; число рейтинга — общее.

### Вход в приложение

- `CommunityGate`, плашка «Сменить» и `state/community.ts` удаляются.
  Клиент больше не шлёт `X-Community-Id`.
- Ссылка из группы с идентификатором команды (`c{id}_...`) открывает нужный раздел
  и служит **поводом проверить членство**: клиент один раз вызывает небольшой
  эндпоинт «присоединиться» с этим `id`, сервер проверяет человека в Telegram и
  создаёт строку `memberships`, если её нет. «Текущую команду» она не выбирает.
  Без этого новый игрок, открывший приложение из группы, не попадёт в неё:
  группы ищутся только среди уже существующих членств. Ссылки на матчи работают
  как раньше: `/context?eventId` тоже проверяет и создаёт членство. *(Решение
  исполнителя-автора документа, по замечанию проверяющего.)*
- Человек без групп: «Главная» и «Матчи» показывают пустое состояние с инструкцией
  подключения бота. Профиль работает.

### Бот

- Личные команды `/matches`, `/payments`, `/settings` работают по всем группам сразу,
  без вопроса «какая команда». Группа подписывается в тексте, если групп больше одной.
- `/newmatch` в личке: одна группа с правом создания — сразу; несколько — выбор,
  как сейчас; ни одной — объяснение.
- Сообщения в группе используют общее имя пользователя.

### Существующие данные

Миграция `0009_multiple_groups.sql` ещё не закоммичена и не применена в production.
Её часть, которая переносит профиль в `memberships` (`display_name`, `kaspi_phone`,
`profile_completed_at`, `playing_position`, `dominant_foot`, `notifications_enabled`),
убирается: поля остаются в `users`, где они были. Колонки `active`, `telegram_admin`,
`legacy` остаются.

`skill_assessments` меняется отдельной новой миграцией: для каждого пользователя
остаётся самая свежая анкета (по `created_at`), затем таблица пересоздаётся
с ключом `user_id`.

Если локальная база разработчика уже содержит данные с разными значениями в
`memberships`, их можно не переносить: production их не видел.

## Что остаётся исполнителю

- Точные формы URL для `/members` с группой.
- Как хранить и считать список подтверждённых групп за запрос: сейчас
  `confirmedCommunities` делает запрос в Telegram на каждую группу. Можно
  кешировать по `checkedAt`, как это делает `confirmedMembership`, если в старом
  документе это уже не решено иначе.
- Палитра цветов для подписи групп в рамках `DESIGN.md`.
- Порядок разделов на экране «Игроки» (предлагается по названию).
- Обновление тестов, которые завязаны на `X-Community-Id`, и `DESIGN.md`
  (раздел «Navigation and screens» и описание листа создания).

## Проверка

- Пользователь без групп: входит, видит профиль, пустую ленту с инструкцией,
  кнопка «Создать матч» объясняет, что делать.
- Одна группа: ни плашки, ни подписей, ни поля «Группа»; всё как раньше.
- Две группы, организатор в обеих: общая лента с подписями, выбор группы в
  «Новом матче», матч создаётся в выбранной.
- Две группы, организатор только в одной: поля «Группа» нет, матч создаётся
  в той, где он организатор. Попытка API создать в другой → 403.
- Игрок другой группы не видит матчи, счета, игроков и историю чужой группы
  через API (подмена `eventId`, `billId`, `userId`, `communityId`).
- Рейтинг игрока одинаковый во всех разделах «Игроки» и учитывает матчи обеих групп.
- Изменение имени или Kaspi видно во всех группах; открытые счета обеих групп
  обновились.
- Существующие тесты, проверка типов, сборка и браузерные сценарии проходят.
